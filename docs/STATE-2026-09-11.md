# State of play — 2026-09-11

Written at the end of the probe session. Read this first next time.

## What is settled, by measurement

Four runs on a real storefront (`pusha-probe/results.md`), one
variant per loading shape, 4 navigations each.

**Two shapes recover with zero configuration and zero cost:**

1. **The app listens for `shopify:page:view`** — Shopify's Standard Storefront Events
   vocabulary. Pusha already dispatches it on every swap via the `standardEvents`
   bridge. Measured: rebinds every nav, no double-init.
2. **The app block is a custom element** — `connectedCallback` re-mounts it. The only
   shape immune to every intervention tested.

**Everything without a re-init hook is dead, and loading shape is irrelevant.**
Schema-attribute JS in `<head>`, inline `<script>` in markup, in-markup `<script src>`,
and `type="module"` all failed identically. This kills "re-execute the scripts in the
swapped markup" as a general remedy — for the canonical case the JS is never in the
markup at all.

**`appCompat.sectionEvents`** — narrow but safe. Recovers apps that already listen for
`shopify:section:load`, and lets shell-resident code repair a block it does not own.
Zero accumulation. **Cannot reach designMode-gated apps**, which is a whole class,
because Shopify's own docs tell app developers to gate on it.

**`appCompat.reexecuteExtensionScripts`** — effective and harmful. The only mechanism
that revives an app with no hook at all, at the cost of **unbounded listener
accumulation**: re-execution adds an execution, it does not replace one. One listener
became five over four navigations.

**Both flags together: never.** They compound multiplicatively. A variant clean under
either flag alone recorded 14 double-inits under both. `warnOnConflictingAppCompat`
now fires at boot on `debug`.

## What is settled, by documentation

Two more recovery shapes exist that the probe could not model, both found by reading
vendor docs:

3. **The block has no JavaScript** — pure Liquid/metafield output. Six of Judge.me's
   seven widgets are this shape and always survive.
4. **The app publishes a public API returning rendered HTML** — Judge.me's
   `GET /widgets/product_review` takes a public token and returns embeddable HTML.
5. **The app publishes a re-init call** — Zapiet's `Zapiet.start()` / `zapiet:start`,
   documented for AJAX cart drawers.

## The open question

**Adoption, not capability.** The mechanism is proven end to end. What is unmeasured is
how many installed apps have adopted any of these shapes. Five data points so far, and
**not one of the five listens for `shopify:page:view`.** Adoption of the sanctioned
vocabulary is, on this sample, zero.

- **Judge.me** — neither measured shape, but mostly safe anyway because its widgets are
  server-rendered. One broken surface, one documented fix.
- **Zapiet** — neither measured shape, but publishes a reload call. **High severity**:
  an inert widget loses cart attributes and the `_ZapietId` line item property, so
  checkout gets wrong rates or the order arrives with no fulfilment instruction.
- **LoyaltyLion** — shape 5, the cleanest fit found. `window.loyaltylion.ui.refresh()`
  is documented for "remove the component, render it again, then refresh", which is a
  container swap described in the vendor's own words. `init` must never run twice.
- **Klaviyo** — shape 0 plus a public tracking API. Officially "Klaviyo doesn't support
  SPA". Forms break with no supported fix; tracking is repairable with `klaviyo.track`.
- **Smile.io** — shape 0 for the launcher and panel, which is most of the product. The
  in-page points blocks look broken and Smile publishes no re-draw call, only a JSON
  data API.

All five are documented in `docs/apps/`. None has been tested on a live store.

**Shape 0 came out of this round and reframes the triage.** An app embed renders in
`layout/theme.liquid`, outside the container, so it is never swapped — which is why
three of the five apps are mostly fine without any adapter. The work is always in the
app *blocks*, never the embed. `pusha audit` already reports the split; the README's
triage now starts there.

⚠ **Klaviyo may falsify a README claim.** Klaviyo documents that *Active on Site* and
*Viewed Product* are tracked "by Klaviyo via a snippet installed by our app embed", not
by the Shopify pixel. Pusha's README attributes browse-abandonment loss to the app
pixel. If Klaviyo's split is accurate the outcome still holds — a once-per-document
snippet fires once — but the channel is wrong and the fix is two lines of theme code
rather than a companion pixel. **Measure before editing the README.** Details in
`docs/apps/klaviyo.md`.

## Still unanswered

  (`docs/questions-for-shopify-dev.md` Q7b.) One `fetch()` settles it. Devrel could not.
- **Probe H's captured reference** — the embed stale-reference failure. The variant is
  built and deployed; nobody clicked "check ref".
- **Whether the API-backed and re-init-call shapes generalise** beyond these two apps.
- **Whether Klaviyo's *Viewed Product* really stops on a swap**, and whether re-firing
  it from `onAfterInit` double-counts. One probe run on a published store settles both.
- **What Smile's in-page app blocks actually render.** Their markup is not published and
  two help articles 404. The Quick View limitation is indirect evidence, not proof.

Answered since: **Judge.me has no undocumented re-init call** — searched across
community, code search and integration docs, negative result recorded in
`docs/apps/judge-me.md`.
